## Contract

The next source task may introduce one local modeled peer-output receipt report
for exactly one accepted connected peer and one authenticated, shell-attached
session channel.

The accepted success ordering is:

1. The accepted socket-delivery path establishes the modeled listener,
   connected peer, and SSH-owned connection descriptor.
2. The accepted SSH prerequisites hold on the same modeled connection:
   authentication success, one session channel, shell attachment,
   channel-data/stdio local bridge, channel-window accounting, channel
   lifecycle, and POSIX EOF/wait integration.
3. The service generates only accepted output classes: channel-data stdout or
   stderr bytes, SSH_MSG_CHANNEL_EOF, SSH_MSG_CHANNEL_REQUEST exit-status with
   request type exit-status and want_reply=false, and SSH_MSG_CHANNEL_CLOSE.
4. Each accepted output class is queued by the service through send_ready/send
   on the same accepted stream-socket connection, subject to local
   backpressure.
5. The modeled peer observes the queued bytes by receiving from its peer-side
   stream-socket receive path. Receipt evidence may retain only public output
   class labels, public SSH message names/numbers, public request type names,
   public status values, and length/count categories.
6. Ordering remains channel-data before local EOF, exit-status before close,
   and full channel closure only after both local close and peer close are
   represented by the accepted lifecycle state.

On the accepted local success path the next source task may report a new local
counter/label equivalent to peer-output-receipt-local=true. Existing local
socket-delivery, authentication/session/channel, shell, channel-data,
channel-window, channel-lifecycle, and posix-eof-wait counters may remain true
only when their accepted prerequisites are satisfied by the same modeled flow.

live-reachability=false, remote-receipt=false, compatibility=false, and
ssh-ready=false remain authoritative.

## Failure Contract

All non-success paths must fail closed without accepting peer-output receipt:

- missing listener, missing accepted connection, wrong owner, closed peer,
  hangup/error, or peer-side receive attempted before service output is queued;
- missing authentication, session channel, shell attachment, stdio ownership,
  channel-window, channel-lifecycle, socket-delivery, or POSIX EOF/wait
  prerequisite;
- output attempted before local process completion/status is available, after
  lifecycle closure, after peer close when output is forbidden, or with a
  consumed/missing wait status;
- send backpressure, peer receive-queue exhaustion, over-limit observation, or
  would-block receive;
- duplicate EOF, duplicate exit-status, duplicate close, invalid output
  ordering, malformed lifecycle state, or unsupported output class;
- redaction-sensitive input, command payload, channel data payload, key/session
  material, live peer data, hardware data, or boot artifact attempting to enter
  durable evidence.

Failure evidence must use fixed labels, public message/request names or
numbers, public status values, public count and length categories, readiness
counters, validation commands, task ids, source/doc paths, and classifications
only. Durable evidence must not retain channel identifiers, request payload
bytes, command payload bytes, channel data bytes, key/session material, private
user data, live peer data, hardware data, or boot artifacts.
