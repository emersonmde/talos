## Goal

Talos-owned API boundary for a later operator-seeded CSPRNG implementation.
This task accepts dependency/API strategy only; it does not implement random
byte generation.

## Selected Dependency Strategy

The future core implementation should add only these dependency entries:

~~~toml
chacha20 = { version = "0.10.0", default-features = false, features = ["rng", "zeroize"] }
zeroize = { version = "1.8.1", default-features = false }
~~~

The implementation should use chacha20::ChaCha20Rng plus
chacha20::rand_core::{Rng, SeedableRng} through the rng feature. The direct
zeroize dependency is for Talos-owned seed buffers and temporary output
buffers; the chacha20 zeroize feature ensures the RNG state and buffered output
participate in zeroize-on-drop paths provided by the crate.

Required feature boundaries:

- default-features = false is mandatory for both dependencies.
- Enable only chacha20 features rng and zeroize.
- Do not enable std, default cipher, legacy, xchacha, serde, getrandom, host OS
  RNG, network, hardware RNG, or ambient lab-state features.
- Seed only from the accepted /etc/talos/operator-seed.bin secret-material
  bytes after applying the accepted 32..4096 byte length contract.
- Use a Talos-owned conditioning step to derive the 32-byte ChaCha20Rng seed
  from the bounded operator seed input; the core implementation task must
  define that conditioning directly before generating bytes.

The future implementation must wrap the dependency in a private Talos module.
Talos code must not expose or call dependency helpers that reveal state, such
as seed/state getters, serialized RNG state, stream identifiers, or debug data.
Only the Talos wrapper may own the RNG value.

## Future Internal API Boundary

The future CSPRNG core should expose an internal, non-public ABI surface shaped
around:

- input: read-only VFS metadata plus at most 4096 bytes copied from
  /etc/talos/operator-seed.bin;
- readiness states: missing seed, invalid seed object, insufficient seed,
  conditioning failed, ready;
- errors: fail closed without returning partial output or secret-derived
  identifiers;
- output: bounded caller-provided byte slices filled only after ready state;
- diagnostics: metadata-only readiness labels already accepted by entropydiag
  and sshkeydiag, plus a cryptographic-strength metadata transition only after
  the core task proves sufficient seed conditioning and CSPRNG readiness;
- lifetime: clear temporary seed/conditioning/output buffers before returning
  when possible, retain only private CSPRNG state and readiness metadata, and
  never retain real operator seed bytes in task evidence.

The wrapper must not expose generated bytes to shell diagnostics, serial logs,
task records, debug formatting, stable public ABI, or comparable identifiers.
Any retained evidence may record only public fixture names, lengths,
readiness labels, and validation command results.

## Candidate Review

- selected: RustCrypto chacha20 0.10.0 with default-features=false and
  features rng,zeroize.
  - Cargo metadata shows the crate is no_std, MIT OR Apache-2.0, Rust 1.85
    MSRV, and the rng feature depends on rand_core with
    default-features=false.
  - Source inspection shows ChaCha20Rng implements SeedableRng, TryRng, and
    TryCryptoRng, uses a 32-byte seed, and zeroizes RNG buffered output plus
    zeroize-on-drop paths when zeroize is enabled.
  - Source inspection also shows state/seed getter and serialization helpers
    exist, so Talos must hide the dependency behind a private wrapper and must
    not expose or call those helpers in diagnostics or evidence.
- selected support dependency: zeroize 1.8.1 with default-features=false.
  It is needed directly so Talos-owned seed and temporary buffers can be
  cleared without importing std.
- rejected: rand_chacha 0.10.0 with default-features=false.
  It is no_std and suitable as a deterministic ChaCha RNG, but it does not
  provide an accepted crate feature for zeroize-on-drop of RNG state/buffers in
  this review. RustCrypto chacha20 gives the same ChaCha20Rng shape with a
  narrower zeroization story for Talos.
- rejected: the high-level rand crate and any getrandom/SysRng strategy.
  Those paths risk std/default feature leakage, host OS RNG assumptions, or
  ambient randomness sources outside the accepted Talos seed boundary.
- rejected: direct stream-cipher mode using chacha20 cipher, xchacha, or
  legacy features for this slice. The next task needs an internal CSPRNG
  boundary, not a general stream-cipher API or encryption surface.
- rejected: hand-rolled ChaCha/DRBG implementation. The project direction says
  to use libraries where they reduce risk without hiding kernel
  responsibilities; hand-rolling increases review burden before SSH
  prerequisites are ready.
- deferred: selecting SSH host-key, authorized-key, writable persistence,
  service, live transport, hardware reachability, or public ABI dependencies.

  lock is required for this dependency-selection contract.
